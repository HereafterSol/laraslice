# LaraSlice — After Launch (the SDLC tail)

**Load first:** the `laraslice` core skill. Building the
system is half the lifecycle; this skill is the other half.
Every job below names its three control surfaces — **CLI**
(terminal/cron/AI), **Studio** (the Dev Studio UI), and
**AI** (an assistant holding the skill family) — because a
job that only one surface can do is a gap, and gaps are
named, not hidden.

The golden rule of the tail: **declarations change first,
generated code follows, evidence closes.** Never hand-edit
generated output on a live system; change the Heart, the
Mind, or the Soul, then regenerate and verify.

## 1. Customize — change the living system

| Change | How (any surface) |
| --- | --- |
| Add/change a field | `slice:field` (writes the Heart + one migration) · Studio Design · AI edits `slice.yaml` then regenerates |
| New slice on a live system | The `laraslice-start` dossier rules apply — Mind first if the journeys change |
| Look & feel | The **Soul**: design tokens / DESIGN.md at the standard layer — never per-slice CSS |
| Own a core slice | `slice:publish` moves it into `app/Slices` under project ownership |
| Show/hide a module | `slice:toggle` · Studio Manage |

## 2. Optimize — keep it fast as it grows

| Routine | Command / surface |
| --- | --- |
| Boot performance | `slice:cache` in production (slice discovery cached like routes); `slice:clear` after copying a tree |
| Dead UI weight | `slice:ui:prune` — finds unused BlatUI components across slices |
| Audit-table growth | `laraslice:audit:prune` — the audit trail is on by default; prune it on a schedule |
| Environment sync | `slice:sync` — schemas/versions/migrations across environments (GitOps) |

**Named gap (framework backlog):** there is no built-in
query profiler or N+1 detector yet. Until one lands, slow
surfaces are hunted with Laravel's own tooling (query log,
Telescope in local) and fixed at the declaration (indexes
and eager relations are declared, not patched per page).

## 3. Improve — iterate without breaking truth

The verify loop, in order, after any change:

1. `slice:diff` — what would change in a manifest (writes nothing).
2. `slice:drift` — Mind ↔ Heart drift at zero errors: roles,
   access declarations, and actual grants agree.
3. `slice:links` — every navigation link lands on a real,
   correctly-owned route.
4. `slice:validate` — manifests against the schema.
5. Real-usage journeys (§18 of the core skill): admin AND
   employee, values asserted — a green page is not evidence.
6. `slice:repair` — brings slices generated by older versions
   up to the current layout; idempotent, safe to re-run.

## 4. Operate — the day-to-day

| Job | CLI | Studio |
| --- | --- | --- |
| Health (DB, slices, storage, Mind, audit, runtime) | `slice:operate` | Operate mode |
| Backups — list / run one now (honours the Mind's declared includes) | `slice:operate backups` / `slice:operate backup` | Operate mode |
| Access review (who holds what, drift vs the Mind) | `slice:drift` | Operate mode |
| Workflow SLA breaches | `workflow:sla-check` | Operate mode |
| Operator manual | generated from the Mind (SystemOperate) | Operate mode |

Health exits non-zero on a failed check, so cron/CI can run
`slice:operate` as a watch. **Named gap:** backup *scheduling*
is the host's cron + the Mind's declared cadence — the
framework runs backups, it does not yet schedule them;
non-SQLite backups need a dump tool configured in
`operations` (the command says so when it writes a logical
backup instead of pretending).

## 5. Upgrade — move forward without stranding anyone

- **Framework:** composer update; then `slice:repair` brings
  project slices to the current layout; `slice:cache` refresh.
- **Upstream strategy:** the core skill's §9 (customization &
  upstream updates) is the contract — generated bases are
  regenerated, hand-written subclasses are never overwritten
  (the generation gap).
- **Think existing installs:** every migration must run on a
  system that already has data and users — a change that only
  works on a fresh install is not an upgrade path.

## The SDLC, whole

Discovery → Mind (`laraslice-start`) · Design → Body ·
Build → slices · Verify → gates · Release → the boundary ·
**Customize → Optimize → Improve → Operate → Upgrade → this
skill.** A system is done being built the day it launches;
it is operated for the rest of its life.
